## The five findings that matter most to a field user

1. **Reopening a survey restores no received map (the owner's request).** `open_survey_gpkg` reads only the survey tables, then `reset_survey_workspace` drops every received row (M6 headline). A second press of 지적 / 토양 / 지질 / 수계 does reuse the copy kept in the survey folder; 수치지형 and DEM first demand internet and an account; 유산 cannot receive at all.
2. **Several "load a file" paths say success and load nothing.** Dropping files on the window, the 파일함 list, 벡터·도면 불러오기 and its CAD notice button write 「레이어 N개 추가됨」 or similar but add no layer (M1-3, M5-63, M5-66).
3. **새 조사 / 열기 throw away unsaved work without asking** (M2-1, M2-2, M7-1, M7-2). Arrow keys on the map tab move every trench with no undo (M4-39).
4. **The delivery chain is not usable:** 제출 꾸러미 만들기 and 레이어 5179 변환 are greyed, 인쇄 reports pages sent that were not, 시굴격자 / 등고선 / 정합 report work that did not happen (M2-10, 30, 31, 41-45, 48-50, 53, 54).
5. **Eight 더보기 rows open the API-key window whatever they are called**, and 웹 자료 and 보고서 작성 are missing (M1-4..7, 14, 15, 22, 27, 28..35).

### PART-M6 - received maps: where kept, second press, reopening (C++ vs Rust)

Audit of the C++ reference (`target/cpp-ref/src`) against the Rust app (`crates/strata-app/src` and the crates it calls), read-only.
Citations are `<file>:<line>` for lines that were opened; where two files share a basename the crate or folder is named.
Paths are patterns only: `<survey folder>` = the folder that holds the opened survey `.gpkg`
(C++ `ReferenceStorage::surveyFolder`, ReferenceStorage.cpp:39; Rust `survey_folder.rs:8`).

## Verdict rule used in the last column

The owner's request (2026-11-15 23:40) is two things: (1) a map that was received and added is used again on the next press for the same survey
(no second download); (2) it is shown again when the survey is reopened. The verdict is the WORSE of the two.
SAME = both behave as the C++. DIFFERENT = the button exists and receives/reuses, but the second press or the reopening differs (the cell says which).
MISSING = no such way to receive/reuse in Rust. FAKE = drawn, but the click only sets a flag/message or does something else.

## Headline for the owner's request (what the code does today)

1. **Reopening restores nothing in Rust.** `open_survey_gpkg` reads only the survey tables (gui_tab_home_open.rs:45-46), calls `reset_survey_workspace`
   (gui_tab_home_open.rs:56), which throws away every received row and run (gui_tab_home_survey.rs:105-111), then adds only domain rows + the two default
   background rows (gui_tab_home_open.rs:60-66). The file says itself that restoring the workspace is "아직 없다" (gui_tab_home_open.rs:1-4), and the save
   writes no workspace (survey_gpkg_save.rs:7: "작업공간(.qgz·qgis_projects 쓰기)과 복구 사본은 아직 없다"; `write_survey_to` saves `survey_tables` only,
   app_state_projects.rs:219). So the list of which maps were on the map, with checkmark/opacity/order, is not kept anywhere.
2. **The C++ restores them from the saved project.** `openSurveyGpkg` reads the project that is embedded in the `.gpkg` (MainWindowSession.cpp:301-303) or the
   companion `.qgz` (MainWindowSession.cpp:322-368), then `finishOpenedProject` (MainWindowSession.cpp:149) re-finds moved files (:164) and re-applies the DEM look (:170-179).
   Received files stay outside the `.gpkg` and the project points at them (SurveyStorage.cpp:747 `skippedReference`: external reference/cadastral layers are not copied in).
   The layer is back only if the user saved after receiving (receiving only sets dirty: MainWindowOverlay.cpp:671-672, MainWindowCadastral.cpp:167).
3. **On a press, Rust reuse is uneven.** 지적, 토양, 지질, 수계 look into the survey folder first and put a kept copy on the map with no network
   (cadastral_run.rs:154-158, ref_map_run.rs:162-165) - this is better than the C++, which has no such branch for soil/geology/river (SoilMapService.cpp:271 goes straight to a new folder).
   수치지형 and DEM check "online" and "stored account" BEFORE they look at the folder (topo_download.rs:111-118), so offline or without an account a press shows nothing
   although the files are in the folder; `show_survey_dem` is called only by the scripted snapshot step (snap_shot_steps.rs:97). 유산 cannot receive at all
   (heritage_reuse.rs:22). The tile maps (지형맵, 대동여지도, 1919) are a new press each reopening (cheap: tiles come from the tile cache).
4. **Two different things must be built** (see the list under the table): (a) "restore on open from the folder" with the existing `kept_*` functions,
   and (b) "remember which rows were on the map" (a saved list). (a) alone brings back maps the user had removed, and it silently shows nothing when the survey
   area changed (the match is exact: cadastral_layer.rs:77, ref_map.rs:214-220). That is the director's decision.

### Facts behind the columns, one place

- C++ restore path on open: `openSurveyGpkg` -> embedded project (MainWindowSession.cpp:299-303) -> else companion `.qgz`/`.qgs` (:322-368) -> else only `loadSurveyLayers` (:395) which is the only thing Rust does. Rust `open_survey_gpkg` = that last path (gui_tab_home_open.rs:2-3).
- C++ received files are never copied into the survey `.gpkg`: reference and cadastral layers from outside files are skipped when the project is saved (SurveyStorage.cpp:743-747); only layers living in memory are absorbed.
- C++ `ka-hgis-reference-XXXXXX` folders: a folder replaced by a newer download is removed at the next save (`pruneRetiredReferenceFolders` MainWindowDownloads.cpp:105-115, called MainWindowSession.cpp:1238). Rust never prunes them (grep `ka-hgis-reference` in crates/strata-app/src: only ref_map.rs:231), so each press that fetches adds a folder and `kept_map` picks the newest valid one (ref_map.rs:227-248).
- Rust cannot re-use a map the C++ received for soil/geology/river (no scope note: ref_map.rs:236-238) and the C++ cannot know the Rust note; the two apps' `ka-hgis-reference-*` folders do not mix.
- Both apps keep one tile cache for the whole PC, not per survey: C++ QNetworkDiskCache 2 GB (KaApplication.cpp:817-824), Rust `%LOCALAPPDATA%\ka-hgis\tiles\<kind>\z\x\y` (basemap_fetch.rs:14-18, :56-60).
